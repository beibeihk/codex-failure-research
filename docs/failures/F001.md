**Proposed invariant / expected behavior:** inventory failure from a resource-supporting server must remain
visible in the model-facing result, rather than becoming an unqualified
successful empty/partial inventory.
This is not an established official contract. Best-effort aggregation may be
intentional, and #6217 records a similar asymmetry for a missing optional method.

**Reproduction:** run `python -m harness.replay --codex /path/to/codex --condition
error_aggregate`, then `--condition error_named`. The server advertises resources,
completes initialization, and returns a valid `-32603` resource-list error.

**Expected:** the aggregate call communicates the unavailable server or marks
the inventory partial, while preserving healthy results where possible.

**Actual:** aggregate output is `{"resources":[]}` with `status: completed` and
no error. Named output contains the original error and `status: failed`.
Healthy genuine emptiness produces the same aggregate inventory text as the
failed server. Mixed catalogs omit the failed server without partial metadata.

**Frequency, controls, ablations:** the generated result table contains every
version/platform/condition denominator and exclusions. Windows confirmatory
matrix: 10 repetitions per condition per version. WSL stable validation:
3 repetitions per condition. Pilots are excluded.

**Source mechanism, high confidence:** the aggregate collector logs an error
without retaining it in the returned catalog map; the resource handler then
serializes the map as a successful result. Named calls propagate their error.
Runtime output and fixture-side counters agree with this data flow.

**Hypothesis and limits:** retaining per-server failures/partialness would make
feedback truthful; the exact API design is for upstream discussion. No production
patch or downstream model-task effect is demonstrated. No real model inference
was used. Confidence is high in the observed propagation path and limited in
impact magnitude outside the fixture.
